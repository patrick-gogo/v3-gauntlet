Words

  • Lap: one /v3-lap = one devbox session for a set of tickets, from packing until push day. It has one id (lap-20261006-0944) and its tickets keep their branches for the whole lap.
  • Round: one build-review-test pass inside a lap, ending in a handoff. Round 1 is the first night. Every change you ask for afterwards (from your answers, or from the push-day review) is a follow-up to the same session: round 2, round 3, on the same branches. A new round is never a new lap.
  • New lap: only when you send new tickets with /v3-lap.
  • Wave: every branch merged and deployed to the stack once.
  • Run: one pass of the Playwright matrix, about 14 minutes.
  • Exit pair: two green runs in a row on the same build.

Ruling levels

  • T1 obvious fix (text, typo, CSS nudge): the loop decides.
  • T2 a choice the shop makes (required or optional, limits, defaults): goes ahead with a pick, flagged for the PM before push.
  • T3 business decision (new feature, money, tax): flagged for a full talk with the PM.
  • Unsure between T1 and T2? Treat it as T2.

House rules in the space

  • One heavy thing at a time: builds, the matrix and pytest take turns.
  • Check the stack is free first: pgrep -f "playwright test|exit-pair|deploy-api|build-next"
  • Anything over 10 minutes runs detached.
  • Unclear? Write a ruling and keep going.

Devbox spike results

  • Stack, backend tests, ruff ratchet, frontend build and Playwright smoke all ran unattended.
  • No plugins in the space: the lap rules travel as docs/gauntlet/RULES.md.
  • Uncommitted laptop edits arrive inside a snapshot commit, so laps are packed from a clean copy at master.
  • Only devbox/... branches come home: ticket branches are devbox/<lap>/<branch>.
  • No GitHub access and no Notion token in the space: push day and board updates run on the laptop.
  • 12 GB RAM, no swap: one heavy thing at a time.

1. Once per lap
Stack up and gates baselined on master. The 10-minute cold start is paid once, not three times.
2. One ticket at a time
Each ticket on its own branch from the same clean master, built test-first and reviewed until PASS (parallel is off: one heavy thing at a time).
3. Wave
All reviewed branches merged into a throwaway branch and deployed: catches tickets that pass alone but clash together.
4. Run + triage
Gates, Playwright and a cross-branch audit on the combined code. A product bug goes back to that ticket only (pink "fix"), then a new wave.
5. Exit pair
Two green runs in a row on the same combined build.
6. One handoff
Section 0: every question across the 3 tickets. Then a table: each ticket Ready or Needs you.
  • Morning: /v3-lap result moves each card; one reply answers all questions; /v3-lap push opens one draft PR per Ready ticket you approve.
  • Stop time: a ticket not started by 06:30 comes back as Needs you ("not reached").
  • Budgets are per ticket, so one hard ticket cannot eat the others' share. Three tickets use about three times lap 1's usage of the shared account.
  • A merge conflict between tickets that is not trivial drops the later ticket from that wave, with a note in the handoff.

LAP vs ROUND (from a real lap)

One lap, several rounds. Every round after the first is a follow-up to the same devbox session, on the same branch. Read top to bottom:
Lap starts
/v3-lap packs ticket ABC-123 from a clean copy of master and starts one devbox session: lap lap-20261006-0944, branch devbox/lap-20261006-0944/bugfix/ABC-123-....
Round 1 (devbox)
Builds test-first, reviews, runs the gates, writes the handoff. Status: Ready.
Result + answers (laptop)
/v3-lap result brings it home. You answer "1 keep 2 yes". No change asked, so nothing goes back.
Push day review (laptop)
/v3-lap push checks drift and reviews before pushing. It found master had merged a new tax rule from another ticket after round 1 started. Push stopped, nothing pushed.
Round 2 (devbox, follow-up)
The fixes go to the same session as a follow-up: merge master, change one formula, update tests, new handoff. Same lap id, same branch.
Round 3, if needed
If the spec owner rules differently, one more follow-up to the same session. Still the same lap. Then result, answer, push again.
  • Where a round can start: your handoff answers (/v3-lap answer with a "change"), or the push-day review finding something to fix.
  • What never happens in a round: a push. GitHub only sees the branch on push day, after you say "push".
  • A finished session can still take a follow-up, so a round can start the next morning or days later.
  • New lap = new tickets packed with /v3-lap. Tickets from different laps never share a session.
